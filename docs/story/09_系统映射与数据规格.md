# 系统映射与数据规格（对接现有 Godot 工程）

> 依赖：`01_世界观与核心设定.md`、`02_主角与人物设定.md`、`08_案件_案九至案十.md`。
> **本文件只描述"剧情如何落到现有代码上"，不新增引擎概念、不要求改动核心层。**
> 对接的真实接口以本文件列出的签名为准（已核对 `scripts/core/`、`scripts/data/` 源码）。

---

## 1. 总映射表（世界观 ↔ 现有系统）

| 世界观概念 | 现有系统 / 接口 | 说明 |
| --- | --- | --- |
| **余页** | `TimeLoopManager`（Autoload） | 一段被改动而"没写死"的时间，反复播放 |
| **第几遍存思** | `TimeLoopManager.get_loop_index()` / `signal loop_started(loop_index)` | 直接复用；`loop_index` 从 0 起 |
| **余页长度** | `TimeLoopManager.get_loop_duration()` | 由本案 `npc_timelines.json` 的 `meta.loop_duration_seconds` 设定（各类案不同：案九 540、案十 420） |
| **余页的钟** | `signal time_updated(current_second)`（**剩余秒数**） | UI 代号"漏刻"；注意语义是 remaining，而 NPC 动线用 `second` = elapsed |
| **余页结束** | `signal loop_reset` | 世界观里叫"这一页又翻回去了"；订阅者在此清理仅属于上一遍的世界状态 |
| **补写成功** | `TimeLoopManager.start_loop()` 之后**不再触发** `loop_reset`（由案件脚本锁定） | 余页被补写死，循环终止 |
| **录中所得（线索）** | `PersistentMemoryManager.add_clue(clue_id, source_loop)` / `has_clue()` / `has_all_clues()` / `get_clues()` | **跨遍保留**，与"线索不会因重置丢失"的铁律天然一致 |
| **线索来源遍数** | `add_clue(id, TimeLoopManager.get_loop_index())` | 存档里记下"第几遍照见的"，用于复盘面板 |
| **活人动线** | `NPCTimelineParser` + `data/npc_timelines.json` | 活人不受余页影响 → 动线每遍一致 → **差异即线索** |
| **辨笔 / 缝** | 剧情层：`clue_id` + 比对面板 | 每案的"缝"由证据链 4–6 环的线索集齐后判定 |
| **心灯** | 新增轻量组件 `scripts/entities/heart_lamp.gd`（**不改核心层**） | 主角身神之象；进余页消耗、结案回复 |
| **校勘记** | `PersistentMemoryManager.get_save_data()` / `apply_save_data()` | 校勘记 = 存档里线索集合 + 来源遍数 + 玩家自注 |

## 2. 每案的数据落点（案件 → 文件）

一个"案"= 一个余页 = 一张动线表 + 一组线索 + 一段剧情文本。

```
data/
  scenarios/
    case_01_baihu.json          # 案一《白鹄不举》 余页 360 秒
    case_02_jiangbi.json        # 案二《降笔不歇》 余页 300 秒
    ...
    case_09_shanlu.json         # 案九《删录》     余页 540 秒
    case_10_diyihang.json       # 案十《第一行》   余页 420 秒（= DEFAULT_LOOP_DURATION）
```

**为什么每案一个文件**：`NPCTimelineParser.load_from_file(path)` 支持任意路径，
且 `meta.loop_duration_seconds` 是权威循环长度（由引导层读取后设定 `TimeLoopManager`）。
因此"每案不同长度的余页"不需要改引擎——**换文件即可**。

## 3. 场景数据规格（在现有 schema 上的**追加字段**）

现有解析器只认 `meta` 的 `schema_version / map_id / loop_duration_seconds / rooms` 与 NPC 的
`npc_id / display_name / default_room / timeline[]`，节点字段为
`second / room / action / facing / dialogue_id / clue_id / note`。

**本作追加一个 `meta.secret`（"缝"的定义）**。为保持向后兼容，**仍写 `schema_version: 1`**，
追加字段对旧解析器是可忽略的额外键（解析器只取它认识的字段）。

```jsonc
{
  "meta": {
    "schema_version": 1,
    "map_id": "maoshan_yuchen_hall",
    "case_id": 9,
    "case_title": "删录",
    "loop_duration_seconds": 540,
    "rooms": ["yuchen_office", "yuchen_courtyard", "yuchen_hall", "yuchen_archive", "yuchen_gate"],
    "description": "卷五·案九：玉晨观整理室。东西会随遍数变少，玩家须抢记。",

    // ── 追加：本案的"缝"与补写条件（对旧解析器无副作用）──
    "secret": {
      "kind": "generation_number",          // 缝的类型：代次数字
      "target": "谱系第三十七代",            // 被改掉了什么
      "motive": "五说并存取一为准",          // 改成这样的理由（必须站得住）
      "note": "不删条目，只修订条目；合并比删除更难查。",
      "per_loop_mutation": {                // ★ 每遍世界的变化（本作的核心差异来源）
        "mode": "shrink",                   // shrink = 每遍变少（案九）/ grow = 每遍变多（案十）
        "affected_rooms": ["yuchen_archive"],
        "affected_entities": ["draft_sheet_04"],
        "note": "铁柜工作底稿每遍少一项，玩家须在任一遍抢记。"
      },
      "resolve_conditions": {               // 补写条件（全部满足即结束余页）
        "require_clues": ["clue_91_paper_grain", "clue_91_box_missing", "clue_91_signature"],
        "require_min_loop": 12,             // 至少第 12 遍（0 起）才可回照全页
        "require_ritual": "huizhao_fullpage"
      }
    }
  },

  "npcs": [
    {
      "npc_id": "npc_91_muqing",
      "display_name": "穆青",
      "default_room": "yuchen_office",
      "timeline": [
        { "second": 0,   "room": "yuchen_office",  "action": "unroll_scans",  "facing": "west",  "dialogue_id": "m_q_00_unroll",     "clue_id": "", "note": "摊开复印件，可从纸质入手。" },
        { "second": 120, "room": "yuchen_archive", "action": "fetch_kit",     "facing": "north", "dialogue_id": "m_q_01_fetch_kit",  "clue_id": "clue_91_paper_grain", "note": "首次目击解锁：纸是 1980 年代的机制纸。" },
        { "second": 300, "room": "yuchen_courtyard","action": "take_break",   "facing": "south", "dialogue_id": "m_q_02_break",      "clue_id": "", "note": "她会在这里第一次说出那句话：活人的动线没被改过。" }
      ]
    }
    /* 其余 NPC 见 08_案件_案九至案十.md「活人动线」小节，直接按该表誊写 */
  ]
}
```

### 3.1 字段合规注意（照 README §3 的校验规则）

| 规则 | 本作要求 |
| --- | --- |
| `second` 必须 `0 <= second < loop_duration` | 所有节点严格小于 `loop_duration_seconds` |
| 每个 NPC 必须有 `second: 0` 节点（否则仅警告） | **一律补齐第 0 秒节点**，不留警告 |
| 同一 NPC 同一秒不得重复（否则**报错**） | 编排时按秒排开 |
| 节点须按 `second` 升序 | 写作时即按升序 |
| `room` 必须在 `meta.rooms` 内 | 新增房间必须同步进 `rooms` |
| 未列出的时段沿用最近一个已生效节点 | 动线表**只需写"变化点"**，不必写满全程 |

## 4. 线索规格（`clue_id` 命名与状态）

### 4.1 命名规范

```
clue_<案号两位>_<对象>[_<细节>]
```

示例：`clue_91_paper_grain`、`clue_101_seals_cold`、`clue_02_li_script_hand`。
**同一 `clue_id` 全作唯一**；跨案共用线索（如 `clue_base_zheng_signature`）不带案号，前缀 `clue_base_`。

### 4.2 线索的三种状态（**不新增接口**，用"包装"实现）

`PersistentMemoryManager` 只有"有/没有"两种状态。本作需要的三种状态用**命名约定 + 一层案件脚本**表达，
**不修改核心层**：

| 状态 | 世界观含义 | 实现 |
| --- | --- | --- |
| **已入录** | 存思照见、出余页后仍在的证据 | `add_clue()` 正常调用 |
| **未入录（自注）** | 主角自己补写的那一格；存在但"不算数" | 单独前缀 `note_`（如 `note_91_gen37`），仍走 `add_clue()`，仅由 UI 区别显示 |
| **被删（封印）** | 反派改掉、需要玩家"抢记"才能留住的条目 | 记录为 `sealed_<原 id>`；若玩家未在本遍抢到，则**只留下 `sealed_` 记录**（用于结局差分：没抢到的条目，在终局校勘记里显示为"[此处缺损]"） |

> **结局判定的现成工具**：`has_all_clues([...])` 直接用于"是否集齐十一遍拓片"这类判定（案十）。
> 例：`has_all_clues(["clue_101_rub_01", ..., "clue_101_rub_11"])` → 开启受录仪式。

### 4.3 调用示例（与现有 API 逐字一致）

```gdscript
# 首次目击解锁（来自 npc_timelines.json 节点的 clue_id）
if TimeLoopManager.get_loop_index() >= 0:
    if PersistentMemoryManager.add_clue("clue_91_paper_grain", TimeLoopManager.get_loop_index()):
        print("入录：纸是 1980 年代的机制纸（第 %d 遍照见）" % TimeLoopManager.get_loop_index())

# 抢记：只在"东西还在"的那一遍成功
func grab_draft_sheet(sheet_id: String) -> void:
    if scenario.sheet_exists(sheet_id):
        PersistentMemoryManager.add_clue(sheet_id)
    else:
        PersistentMemoryManager.add_clue("sealed_" + sheet_id)   # 留下缺损记录
        print("未及抢记：%s 已自行消失" % sheet_id)

# 案十：拓片集齐判定
if PersistentMemoryManager.has_all_clues(rubbing_ids):
    unlock_ritual("zongtan_jiaolu")
```

## 5. 心灯（唯一需要新增的轻量组件）

**放置位置**：`scripts/entities/heart_lamp.gd`（`scripts/entities/` 目前为空，正是玩法层位置）。
**原则**：**只订阅信号，不修改核心层**。核心层保持对 UI/玩法零依赖。

| 项 | 设定 |
| --- | --- |
| **本质** | 主角"身神"的存量。世界观上是"名籍上还没被划掉的那一部分" |
| **计量** | `int`，范围 `0–100`。结案后按周恢复 |
| **消耗** | 进入余页：每秒 -0.02（M2 平衡调整：原 0.05 会让正常玩法的 9 遍额外扣 -54，与重开的 -64 叠加必然熄灯、`require_min_loop: 8` 的案子永远结不了；重开消耗保持不动，见 `04` 的跨案预算表）；**每一遍重开（`loop_index` 递增）：-8**（这是核心压力：反复推演是有代价的） |
| **恢复** | 现实时间（余页之外）按分钟 +1；结案 +25；服饵断谷（案四后）消耗减半 |
| **归零** | **不是死亡**。触发 `heart_lamp_extinguished`：主角被"从录上划掉一笔"，永久丢失一条线索的记忆（UI 上该线索变灰，仍存在于存档，但不可用于推理） |
| **显示** | HUD 上一盏灯。终局选择后不再显示数值，只显示两个字："已录"（见案十） |

**接口草案**（供实现阶段用，不影响剧情文档）：

```gdscript
extends Node
signal heart_lamp_changed(value: int, max_value: int)
signal heart_lamp_extinguished(lost_clue_id: String)   # 归零：丢一条线索的记忆

var _value: int = 100

func _ready() -> void:
    TimeLoopManager.loop_started.connect(_on_loop_started)

func _on_loop_started(loop_index: int) -> void:
    if loop_index > 0:
        drain(8)          # 每重开一遍，身神消耗

func drain(amount: int) -> void: ...
func restore(amount: int) -> void: ...
func get_value() -> int: ...
```

> **为什么不做成"体力条"**：本作的资源不是体力，是**记忆**。
> 心灯归零的惩罚必须落在"线索不可用"上，而不是"跑不动"，否则主题会被玩法消解。

## 7. 三条铁律的**可测试**表现（供后续写自动化测试）

| 铁律 | 可观测断言 |
| --- | --- |
| 一·改录→名实裂缝 | `loop_reset` 后，`TimeLoopManager.get_loop_index()` 递增，但 `PersistentMemoryManager.get_clue_count()` **不变**（现有测试已覆盖此铁律，本作直接继承） |
| 一·每遍的差异 | 案九：同一 `affected_entities` 在 `loop_index` 增大后 `sheet_exists()` 由 true → false；案十：`npc_105_unnamed` 在 `loop_index < 4` 时不可见 |
| 二·不许宣泄 | 每调用一次 `explain_truth(evidence_id)`，`HeartLamp.get_value()` 下降固定值，且对应记忆线索被打上"不可用"标记；**同一内容只收一次费**（幂等，对应 `add_clue` 的幂等语义） |
| 三·期会日 | 每案的 `resolve_conditions` 必须绑定到一个期会日场景；测试断言：未在死线前满足条件 → 进入非好结局分支 |

> **验收建议**：实现阶段为每案补一个无头测试，沿用现有 `tests/test_phase1_smoke.gd` 的
> "执行数量守护"模式（GDScript 运行时错误不会让退出码变红，必须用计数器兜底）。

## 8. 明确**不做**的事（防止实现阶段跑偏）

1. **不修改 `scripts/core/` 三个脚本**。它们的职责边界已在 README §2.1 定死，本作全部需求都能通过"换数据文件 + 加玩法层脚本"满足。
2. **不给 `PersistentMemoryManager` 加"删除线索"接口**。它的"没有重置路径"是核心铁律；"被删的字"用 `sealed_` 前缀在**线索层**表达，不改核心语义。
3. **不使用 `Engine.time_scale`**。流速缩放一律走 `TimeLoopManager.set_time_scale()`（避免连带改变物理与动画）。
4. **不把心灯做成血条**。见 §5 的说明。
5. **不引入 EventBus**，除非跨系统事件超过 5 处；本作目前只需各自动加载的信号（与 README §6 的结论一致）。

## 9. M1 实现期定下的接口口径（写代码时的裁定，回头不再逐条讨论）

M1 把切片升级成玩法层时，数据里原本含糊的地方由实现方拍板并落到代码/测试里。以下是**已经写进代码和测试**的口径；
改数据或换表现层时按这里来，别各自解释。

### 9.1 对话的秒级锚定

| 问题 | 裁定 | 落在哪 |
| --- | --- | --- |
| 对话"第几秒能问"以什么为准 | 以**场景节点**为准：`data/scenarios/case_01_baihu.json` 里 `npcs[].timeline[].{second, dialogue_id}` 是唯一秒级锚点（案一 29 处引用） | `scripts/data/dialogue_loader.gd` 的 `load_dialogue_anchors()` / `apply_anchors()` |
| 对话条目自己没有秒字段怎么办 | `data/dialogues/case_01_dialogues.json` 的条目**没有** `second`/`min_seconds`：`DialogueLoader.DEFAULT_MIN_SECONDS = 1`，`is_active_at(second)` 只在锚点那一秒（`[anchor, anchor + max(min_seconds, 1))`）为真 | 同上，`:52`、`:197-204` |
| 那一秒太窄，玩家点不到 | **表现层用"宽窗口"**：`slice_hud.gd` 的 `_talk_windows` 取"该 NPC 停在这个房间的整段时间"（锚点秒 → 他下一个节点的秒），`_entries_to_say()` 只吃这个窗口；loader 的严格窗口只用于数据自检 | `scripts/ui/slice_hud.gd` 的 `_build_talk_windows()` |
| 没有锚点的条目 | 不主动说；只通过选项的 `goto` 被追到（案一 9 条 goto 专属条目） | `DialogueLoader.is_available()` |
| `speaker` 是中文显示名 | 是真的中文名（"邱德茂"），表现层用 `CaseLoader.NPCSchedule.display_name` 反查 `npc_id`；`npc_id_of(speaker)` 提供同一张表 | `scripts/data/dialogue_loader.gd` |

### 9.2 线索入账的幂等责任

对话选项的 `add_clue` 是"对话 → 线索"的**唯一出口**。去重责任在**记忆层**：`PersistentMemoryManager.add_clue()` 幂等，
表现层（`_speak()` / `_check_observations()`）直接调用、不自己判重；`HeartLamp` 只负责"这条记忆还在不在"（灯灭期间拒收）。

### 9.3 画符（仪式）的输入口径

| 问题 | 裁定 |
| --- | --- |
| 一笔怎么表示 | 一笔 = 一串**方向 token**（8 向：`up/down/left/right` + 四斜向，见 `data/runes/case_01_runes.json` 的 `inputs.tokens`） |
| 怎么判对错 | **只比笔数 + 每一笔的方向串**，不比手速、长度、曲线、压感；错笔分三类：`near_miss`（数据里预置的说法，原文照抄给玩家）与兜底 `wrong` |
| 键位 | 四正方向 = 方向键；四斜向 = 小键盘 `1/3/7/9`（`key_map`），没有小键盘时用 `key_map_alt` 的组合键；退格退一个 token（空了整笔退）、回车落笔/推进 |
| 判定归谁 | 输入层（`scripts/entities/rune_input.gd`）判；表现层只负责收键与显示，**不自己比对方向串** |
| 画错有什么代价 | 没有惩罚：不扣心灯、不判负（`data/runes/case_01_runes.json` 的 `failure_note`）；仪式只是确认，不是打击（`docs/story/04:405-411`） |
| 仪式与结案的关系 | `meta.secret.resolve_conditions.require_ritual` 是**硬门槛**：线索齐 + 遍数够 + 仪式做完，三条同时满足才结案（`slice_hud.gd` 的 `_check_resolution()`）。仪式数据读不进来时放行，只在日志里说明——数据出问题不该把玩家锁死在案里 |
| 重开一遍 | 画到一半遇上 `loop_reset` ⇒ 输入层清掉这一遍的绘制状态（`docs/story/09:17` 的同一原则：只属于上一遍的状态必须清掉） |

### 9.4 观察点遍数锁（M2 平衡期加入）

* 数据位置：`data/scenarios/case_01_baihu.json` 的 `npcs[].timeline[]` 节点上的 `loop_min`（整数，缺省 0 = 哪一遍都看得见）。
* 语义：站对房间、站对时辰、`TimeLoopManager.get_loop_index() >= loop_min` 才入录；遍数不够时表现层只提示一次
  「（这一处还没到时候：要第 N 遍才看得出来）」，不入账、不扣心灯。载入器在 `CaseData.clue_events()` 里带出该字段
  （`scripts/data/case_loader.gd` 的 `TimelineNode.loop_min`）。
* 案一取值（依据 `docs/story/04_案件_案一至案二.md` 的「获得方式」）：四字位 2、拓本残纸 2、半笔寸 3、灰布袋 4。
  也就是六条必需线索里四条要跨遍，和 `require_min_loop: 8` 一起构成"多遍推进"的节奏。
* 校验：`tools/validate_data.gd` 报 `loop_min` 为负 = error、> 12 = warning、有遍数锁却没有 `clue_id` = warning。
